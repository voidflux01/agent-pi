# agent-pi 产品定位（Positioning）

> 状态：v1.1 · 2026-09-08 · 定位由维护者本人确认：个人驾驶舱 + 收敛到被验证路径。
> 修订：v1.1 加入 §7「底座一等公民」+ 顶部理论底座。
> 本文在文档体系中位于最高层：定义「建什么」，`design-charter.md` 定义「怎么建」，`iteration-roadmap.md` 定义「下阶段建什么」。

**理论底座**：设计哲学对齐 Andrew Ng《AI Engineering Skills Map: Using Coding Agents》(2026-09-04) —— spec 先行、验证为核心、自治分级校准、人类高技巧介入优于超长自治、常规修剪与清 agent 债。Ng 框架描述的是「人的元技能」，本仓只采纳其判断，不逐条当功能清单造模块。

## 1. 一句话定位

**agent-pi 是作者（一个人）的 Pi 日常驾驶舱：把自己可信赖的编码与多 agent 工作方法，固化成可复用的模式、agent、门禁与工具，随用随验。**

Pi 是引擎；agent-pi 是作者给引擎装上的驾驶舱和操作手册。它不替代 Pi，不服务陌生用户，不是通用 agent 平台。

## 2. 为何存在 / 解决什么问题

作者是 AI 重度使用者，把复杂工作交给多 agent 执行。随之而来的真实问题不是「缺功能」，而是：

1. **不可信** —— agent 自报完成 ≠ 完成，需要证据与独立验证。
2. **失控** —— 工作流、委派、恢复、上下文一多，单一 agent 会话装不下，多 agent 又各自为政。
3. **不可复现** —— 一次成功不保证下次成功；方法只存在作者脑子里，不沉淀。
4. **无边界** —— 高风险的写、外联、部署动作缺少人审门禁。

agent-pi 的回答：把「我信任的做法」编码成 **契约（RESULT）+ 门禁（gate）+ 证据（evidence）+ 工作流（mode/chain/pipeline）**，让每次执行可解释、可回滚、越用越可靠。

## 3. 目标

**近期（可掌控）**
- 作者能独立解释一次完整任务从「进入」到「验证收据」走通哪几个文件。
- 树内无死代码、无平行实现；每个强制点（gate）可指认代码与测试。
- 常用真实任务（含多文件）能稳定走通至少一条验证路径。

**中期（可积累）**
- 核心工作负载（§5）成为「默认好走、失败可诊断」的稳定路径。
- 方法沉淀为契约与门禁；新增能力必须先在真实验证上证明价值，再进主干。

**长期（可演进）**
- agent-pi 成为作者可信赖的第二大脑外壳：新任务类型被驯服后，被固化为新模式/链/门禁。

## 4. 非目标（明确的「不做」——防止再度膨胀）

- ❌ **不是可分发的商业产品**：不迁就陌生用户、不承诺向后兼容、不做默认配置的通用性打磨。
- ❌ **不是通用 agent 编排平台**：不为「别人可能想要」造抽象。
- ❌ **不是监控/部署/CI 平台**：不做长驻 daemon、不建外部记忆服务、不替用户部署。这些只做只读 adapter 或检查清单，且只在真需要时加。
- ❌ **不为功能而功能**：六模式、viewer、workflow 工具，若没有真实任务在用它，就删除或降级，不留「覆盖矩阵」式摆设。
- ❌ **不追逐 roadmap 全部阶段**：`iteration-roadmap.md` 的 P1/P4（eval/judge、monitor/deploy）等异步能力，若对作者真实工作负载无杠杆，标注 descope，不因「文档写了」而实现。

## 5. 核心工作负载（被验证的主路径）

个人驾驶舱只承诺把下列做扎实；其余均为可选能力，按 §8 收敛原则取舍：

1. **计划 → 实现 → 独立验证**（PLAN→BUILD→REVIEW / verify_execution 收据闭环）。
2. **单次可靠委派**：把一个子任务交给 worker，拿回符合 RESULT 契约、经 reviewer 门的结果。
3. **批量并行 + 恢复**：一批独立任务分波调度，失败/中断可恢复续跑。
4. **安全边界内的项目工具**：受门禁的 bash/文件/浏览器 viewer。

若某编排模式（如完整 PIPELINE 多阶段并行）长期无真实任务使用，则降级为「手动可触发」而非「默认维护」。

## 6. 设计方法（如何做到）

1. **个人偏好即需求**：作者真实怎么工作，就怎么设计；不为想象中的用户调优。
2. **真实验证先于扩展**：新能力先进 `evals/` 或 validation-log 真跑一轮，证明提升真实任务成功率后才进主干。
3. **收敛优先**：每条路径只留一条已验证实现；平行实现与候选模式，未胜出即删（git 考古）。
4. **默认删除**：非核心、无真实调用、纯探索性代码，删比留好。
5. **契约与门禁承载信任**：不靠 prompt 承诺，靠 `## RESULT` + gate + evidence 落地。
6. **人审一切自动化边界**：写/外联/部署类动作必须过人工门禁。
7. **自治分级校准（Ng）**：同一任务先低自治、交互式跑通，确认后按需委派/并行；不默认无人值守超长跑（Ng：超长 horizon 的 ROI 被夸大）。
8. **验证匹配任务（Ng）**：功能/行为/安全验证按需组合；eval-set 只在定性/行为判断需要时引入，不为造平台。
9. **失败模式分级**：能确定性判定的失败模式做成门（未达目标、缺验证、破坏动作）；本质启发式的（过度工程）只做评审准则，绝不造假门。

## 7. 底座：驾驶舱一等公民（Coding Agent Foundations）

Ng 五技能里，foundations 是其余四项的地基。在本仓落成一句话原则：

> **底座 = 状态可读 + 失败模式有门 + 可转向。** 人因看得见、有门、能转向，才敢委派、才校得准自治度。底座服务于人的高技巧判断，不替人判断。

**失败模式 → 门**（能确定性做门，启发式只做评审准则，绝不造假门）：

| Ng 失败模式 | 驾驶舱对策 | 性质 | 仓库落点 |
|---|---|---|---|
| 过早停 / 未达目标 | spec 定义 done：Objective 非空 + verifier 逐 acceptance 核对，禁止自报完成 | 确定性 | execution-contract + isolated-verifier |
| 缺显式验证失严谨 | 完成唯一出口 = verify receipt，无收据不可 complete | 确定性 | execution-gate / canComplete |
| 破坏性动作 | security gate + rollback viewer | 确定性 | security-guard + completion-report |
| 过度工程 | S1 地图 + review rubric 准则（不造检测器） | 启发式 | reviewer 评审项 |

**状态可读（读状态 + 给处方）**：渲染已算的，不新采集。一份单 run 的仪表盘复用现成模块 —— context-budget 的消耗/压缩阶段、orchestration-run 的 event trail、subagent-widget 的委派图、coordination-state 的验证态 —— 配 standing context + 跑中假设捕获 + retrospective 作为处方口。守住 §4：单 run、有界、无 daemon、无跨会话遥测。

## 8. 对演进（Sweep）的直接影响

定位会收紧 `design-charter.md` 的 sweep 执行口径：

- **S1 地图** 不只分 L0–L5 层，还分「核心 / 可选 / 待裁」三档，并**单独标注底座零件档**（context/run/state/receipt 类模块）；顺带暴露哪些状态「算了没渲染」—— 这本身就是底座实现的工作清单。
- **S2 删除** 从「清已确认死代码」扩为「按个人驾驶舱口径裁减」：未在真实任务中使用的 agent 角色（如 builder-<model> 冗余、探索性 security roster）与编排工具进入候选删除；收敛到 §5 主路径。
- **S4 编排重构** 目标不再是「六模式都对等维护」，而是「核心模式深、可选模式浅」。
- **S5 验证补强** 只服务核心负载的确定性腿，不搭通用 eval 平台。
- **底座渲染**：把 §7 已算状态渲染成一块复用 reports-viewer 基建的「单 run 仪表」，小而收口，不建遥测平台。

## 9. 成功定义（可测）

- 作者一次真实的、含代码改动的多文件任务，能走通 §5 路径 1，拿到 verifier 收据，无人工救火 —— 成功。
- 单 run 仪表可见：一次委派/验证/完成，人能指认它走了哪几步、烧了多少、卡在哪 —— 成功。
- 仓库内 grep 不到死代码 / `retired` / 无引用导出的非核心模块 —— 成功。
- 每次 release，`verify:release` 绿 + 地图与代码无漂移 —— 成功。
